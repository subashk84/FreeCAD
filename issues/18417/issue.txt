### Problem description

If the user Preferences have insufficient precision, the `TestPathToolController` tests fail because the tool diameter of 1.75mm does not make a round-trip accurately enough.

In particular, if the user has selected Imperial decimal units (inches, etc) but not changed the default of 3 decimal places, the test will run with these settings and fail because the round trip passes through the string representation "0.069 in" (perhaps using some other representation for the 'inches' unit), which then converts back to 1.7526mm. This is not within the 0.00001 error allowed by `assertRoughly` so the test fails.

The "0.069" is the 3-digit rounding of the more accurate value of 0.0688976377952755905511811023622 inches.

Conversely, the test also uses `assertRoughly` for other checks even though there is no reason the values should not be exactly equal.

The test should set the precision and units sufficiently to assure the round-trip value is accurate, or use a more lenient error threshold based on the units and precision. If the test changes the settings it must restore them on exit.

It is not clear how the test can effectively change these settings. Although it could (probably) reach in and alter the Parameters in `User parameter:BaseApp/Preferences/Units/Decimals` and `.../UserSchema` it does not appear, from reading the code, that this will have an immediate effect on calculations. These parameters are not monitored for changes, and the actual values used for calculations are only set based on these parameters at certain points, notably when changed Preferences are saved or applied.

On the other hand, changing `assertRoughly` to evaluate an epsilon based on these two settings might produce false positive tests if there is actually an error but it is masked by the current Preferences. On the other (other) hand, doing this would allow tests to be run under various Preferences, avoiding the failure to ever detect an error that only occurs with non-standard Preferences.
